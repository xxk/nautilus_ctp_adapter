# Windows Proxy Service Runbook 设计

**状态**：已采纳
**日期**：2026-04-11
**范围**：`docs/architecture/`、当前 change bundle
**关联 plan**：./plan.md

## 一、现状

当前仓内已经有一篇双网卡代理入口/出口绑定文档，解决的是网络拓扑与地址绑定问题，但还缺两类稳定信息：

1. Windows 上如何把代理稳定托管成后台服务
2. 如何把主机侧检查和客户端侧验证固定成一条可重复执行的链路

如果继续把这两类内容混写在原始网络原理文档里，后续会出现一个问题：读者无法快速区分“为什么这么配”和“具体怎么部署”。

## 二、正式入口与实现落点

1. 正式实现落点：`docs/architecture/Windows代理服务化部署与验证_Windows Proxy Service Deployment And Verification.md`
2. 关联原理文档：`docs/architecture/多网卡代理入口与出口绑定方案_Multi-NIC Proxy Ingress Egress Binding.md`
3. 可发现入口：`docs/architecture/README.md`
4. 当前 change bundle 只负责冻结这三处文档关系，不扩展到代码或 topic 文档

## 三、设计方案

推荐方案是“双文档分层”：

1. 原始双网卡文档继续负责网络原理、入口/出口绑定和常见网络故障
2. 新文档专门负责服务化部署、服务注册、监听验证和客户端验证
3. architecture 索引用来提供稳定发现入口

服务托管方式选 `NSSM`，原因是：

1. 它是通用服务包装器，不要求代理程序自身必须内建 Windows 服务逻辑
2. 配置与回收都比较直接
3. 比“长期前台进程 + 手工窗口保活”更适合稳定运维

## 四、接口与输入输出

本次主要冻结文档中的输入输出口径：

1. 入口地址：`10.168.80.56`
2. 出口绑定地址：`192.168.5.235`
3. HTTP 端口：`3128`
4. SOCKS5 端口：`1080`
5. 服务名：`3proxy-egress`

验证输出口径分两层：

1. 仓内验证：文档存在、索引可达、治理检查通过
2. 目标机实跑：服务状态、端口监听、`curl` 出口公网符合预期

## 五、AI 实现约束

1. 不得把目标机待执行步骤写成已完成结果
2. 不得为追求“看起来完整”而加入未经确认的专有运维命令
3. 不得把网络原理、部署步骤、服务验证混成无层次的一篇长文

## 六、备选方案

备选方案是把服务化内容直接追加到原始双网卡文档中。

不选原因：

1. 原始文档已经承担网络原理说明，再塞入服务托管细节会降低可读性
2. 后续如果要追加计划任务、NSSM、SCM 等多个托管口径，单文档会快速膨胀
3. 双文档分层更容易分别维护“原理”和“运维”

## 七、风险与影响面

1. 当前仓库并不是目标代理服务的真实宿主，因此实跑验证不能在仓内完成
2. 若后续目标机环境禁止 `NSSM`，需要再补一版计划任务或其他托管方案
3. 这次只影响文档可发现性，不影响代码或 topic frontier

## 八、发布回滚与退出策略

1. 若后续判断该 runbook 不应保留，可单独回滚本次新增文档与索引入口
2. 回滚时保留原始双网卡文档，不回退其网络原理内容

## 九、需要沉淀为长期规则的内容

1. 双网卡代理的网络原理与 Windows 服务化部署应分开维护
2. 目标机未实跑时，长期文档必须显式写明“待执行”，不得伪造验证结论

# 跨项目落地手册 / Cross Project Rollout

**创建日期**：2026-03-27
**最后更新**：2026-03-27
**状态**：draft
**目标**：指导你把当前文档闭环执行套件落到另一个项目，而不是只复制文件后停留在“已接入”的假状态。

---

## 一、先说结论

跨项目实施不要按“复制全部文档”来做，而要按下面顺序推进：

1. 先选档位
2. 再建入口
3. 再替换项目专属口径
4. 再跑一个真实试点 change
5. 最后才补守卫与扩展件

如果顺序反了，最常见的后果就是：

1. 复制了很多模板，但没人用
2. 文档里全是别的项目路径
3. AI 入口看起来齐了，但找不到真实验证命令
4. topic / change 混层，最后回到纯口头协作

---

## 二、实施前判断

### 适合直接落地的项目

1. 你预计会持续让 AI 参与开发
2. 项目存在中高风险改动，需要留证和验收
3. 项目不是一次性脚本，而是会持续维护
4. 项目已经有基础文档目录或愿意建立一套基础目录

### 暂时不适合直接落地的项目

1. 只有一次性脚本需求
2. 项目根本没有长期维护计划
3. 团队目前不接受任何文档化变更流程
4. 连最基本的入口文件和测试命令都还没有稳定下来

如果属于第二类，先不要上 Full。最多从 Lite 试点开始。

---

## 三、推荐实施顺序

### 阶段 1：30 分钟内完成最小接入

目标：让新项目先具备“可说清入口、可建 change、可做一次试点”。

要做的事：

1. 把 `docs/doc_harness_kit/` 复制到目标项目。
2. 在目标项目建立一个入口地图文件，例如 `AGENTS.md`。
3. 在目标项目建立 `docs/changes/` 模板落点。
4. 建立一个 architecture 导航入口或等价索引页。
5. 选定 Lite / Standard / Full 其中一档。

这一阶段不要做的事：

1. 不要先抽脚本守卫
2. 不要先补一堆 topic roadmap
3. 不要先改造所有历史文档

交付标准：

1. AI 能找到入口地图
2. AI 能找到 change 模板
3. 人能说清“下一次变更写到哪里”

### 阶段 2：半天内完成项目适配

目标：把当前仓库专属口径替换成目标项目自己的真实口径。

必须替换的内容：

1. 目录职责
2. 正式入口与兼容入口
3. 测试分层与验证命令
4. 部署环境与边界说明
5. 高风险链路的真实样例与最小命令

不要照搬当前仓库的内容：

1. `core/`、`strategies/`、`scripts/` 这样的目录边界
2. `scripts/check_antipatterns.py`、`scripts/verify.py` 这样的脚本名
3. 当前仓库的远端机器和路径
4. 当前仓库的 topic-id 示例

交付标准：

1. 文档里不再出现明显的旧项目路径
2. 入口文档能指向当前项目的真实入口
3. 验证命令在当前项目语境中是可执行或可替换的

### 阶段 3：用一个真实 change 做试点

目标：证明这套包不是纸面规则，而是真能驱动一次交付闭环。

建议试点任务：

1. 一个跨 2 到 3 个文件的中小变更
2. 一个需要明确验收结果的任务
3. 一个不会牵扯远端高风险副作用的任务

不建议作为第一个试点的任务：

1. 大规模重构
2. 真实部署
3. 高风险远端修复
4. 多团队联调任务

试点最小交付：

1. 一个真实 `change-id`
2. 一份真实 `plan.md`
3. 一份真实 `acceptance.md`
4. 一份真实 `ai_constraints.md`
5. 一次真实验证与证据回填

交付标准：

1. 这次 change 能完成从计划到验收到回写的闭环
2. 人工能判断哪些步骤有效、哪些模板太重
3. AI 不需要靠额外聊天上下文也能推进这次 change

### 阶段 4：补治理增强件

目标：在试点成功后，再加守卫、topic roadmap 和高风险规范。

建议顺序：

1. 先补 topic / change 分层
2. 再补 ATDD-lite / BDD-lite
3. 再补分析知识沉淀规范
4. 最后补高风险契约锚点与守卫脚本

原因：

1. 先有闭环，再谈增强
2. 先有真实痛点，再决定要机械化哪些规则
3. 否则很容易一开始就上了太重的治理壳

## 四、目标项目里的实际操作清单

### A. 复制哪些文件

Lite 最少复制：

1. `README.md`
2. `adoption_guide.md`
3. `compatibility_profiles.md`
4. `templates/changes/` 的来源说明或对应模板正文

Standard 额外复制：

1. topic roadmap 入口说明
2. archive 入口说明
3. 分析知识沉淀规范
4. ATDD-lite / BDD-lite

Full 再额外复制：

1. 高风险契约锚点规范
2. 守卫接入清单
3. 任务验证速查表

### B. 目标项目里要新建什么

最低限度新建：

1. 一个入口地图文件
2. 一个导航索引文件
3. 一个 change 模板目录
4. 一个真实试点 change 目录

### C. 第一次接入时必须人工确认什么

1. 目录边界是否符合当前项目现实
2. 验证命令是否真实存在
3. 哪类任务必须建 change，哪类可以免
4. topic roadmap 是否真的需要
5. 归档目录和弃用规则是否成立

---

## 五、我建议的默认打法

如果你要把这套包迁到另一个项目，我建议默认走这条线：

1. 从 Standard 档开始，不要从 Full 起步。
2. 只先接入入口地图、三件套模板、导航索引、adoption guide。
3. 用一个真实中小变更跑闭环。
4. 跑通后再决定要不要补 topic roadmap 和守卫。

这是当前最稳的方式，因为它同时避免了两种失败：

1. 治理过重，团队不用
2. 治理过轻，最后只剩模板文件没有闭环

---

## 六、完成判定

跨项目实施完成，不以“文件复制完”为准，而以以下 4 条同时满足为准：

1. 目标项目已有可发现的入口地图。
2. 目标项目已有真实可用的 change bundle 模板。
3. 目标项目已完成至少一个真实试点 change。
4. 目标项目的 AI 能在不依赖当前仓库上下文的情况下推进该试点。

只要这 4 条还没同时满足，就还处于“接入中”，不能叫“已完成复用”。

---

## 七、你实际执行时的最短版本

如果你现在就要去另一个项目落地，最短操作是：

1. 复制 `docs/doc_harness_kit/`
2. 在目标项目创建 `AGENTS.md`
3. 在目标项目建立 `docs/changes/` 模板落点
4. 把验证命令替换成目标项目真实命令
5. 新建一个真实 change 跑通一次

先做到这 5 步，再考虑剩下的增强件。

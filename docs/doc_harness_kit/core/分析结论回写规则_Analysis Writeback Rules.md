# 分析结论回写规则 / Analysis Writeback Rules

**创建日期**：2026-03-27
**最后更新**：2026-03-27
**状态**：draft
**来源**：抽象自当前仓库的系统分析知识沉淀实践
**用途**：定义系统分析、代码分析或故障分析后，哪些结论必须回写，避免重复分析。

---

## 一、核心原则

**没有回写的分析，不算真正完成。**

分析的目标不只是得到结论，还要让下次的人或 AI 能直接复用结论。

---

## 二、最小回写清单

每次系统分析结束后，至少应回写：

1. 模块职责与边界
2. 关键入口或关键调用路径
3. 核心数据流或调用链
4. 关键配置与运行前提
5. 已验证结论与未决项

---

## 三、最小记录结构

建议至少包含：

1. 背景
2. 分析范围
3. 关键路径
4. 已验证结论
5. 证据来源
6. 风险与未决项
7. 下一步

---

## 四、更新原则

1. 只追加新增且已验证的结论
2. 旧结论失效时要立即修订
3. 不要只记录现象，不记录根因与证据

---

## 五、推荐落点

建议按内容类型回写到目标项目自己的长期文档区，例如：

1. 架构与边界文档
2. lessons learned / fixes / audit / live 这类专题目录
3. 当前 change 的 acceptance 或总结文档

重点不是目录名一致，而是：

**结论必须进入可持续维护的正式文档，而不是停留在聊天或临时笔记里。**

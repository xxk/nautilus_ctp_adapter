# 最小变更闭环模型 / Minimal Change Loop

**创建日期**：2026-03-27
**最后更新**：2026-03-27
**状态**：draft
**来源**：抽象自当前仓库的 `OpenSpec-lite` 实践
**用途**：定义一个 change 从开始到收尾的最小闭环，不绑定具体仓库结构。

---

## 一、最小闭环是什么

一个 change 至少要回答 3 个问题：

1. 什么算通过
2. 这一轮具体改什么
3. AI 或执行者推进时有哪些边界

因此最小 change bundle 建议固定为：

1. `acceptance.md`
2. `plan.md`
3. `ai_constraints.md`

---

## 二、三文档分工

### acceptance.md

负责：

1. 定义通过口径
2. 定义场景与出口条件
3. 记录执行证据与验收收口

### plan.md

负责：

1. 定义本轮范围
2. 拆任务
3. 记录修改边界、验证动作和长期回写目标

### ai_constraints.md

负责：

1. 约束 AI 或执行代理的推进顺序
2. 规定状态同步方式
3. 规定遇阻塞时的处理口径

---

## 三、推荐推进顺序

默认顺序：

1. 先写 `acceptance.md`
2. 再写 `plan.md`
3. 再写 `ai_constraints.md`
4. 再开始实现
5. 实现后执行最小验证并回填 evidence

---

## 四、最小完成定义

一个 change 至少满足以下条件，才算完成闭环：

1. 有明确的通过标准
2. 有真实执行记录
3. 有至少一条可核查 evidence
4. 有明确的收尾结论

不能算完成的情况：

1. 只有代码，没有 acceptance
2. 只有模板，没有真实回填
3. 只有“已完成”口头结论，没有验证证据

---

## 五、项目适配时只替换什么

跨项目复用时，应只替换：

1. 目录路径
2. 正式入口名称
3. 验证命令
4. 环境边界说明

不应替换掉的，是三文档本身的分工逻辑。

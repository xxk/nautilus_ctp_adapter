# 验收场景写法 / Acceptance Scenario Writing

**创建日期**：2026-03-27
**最后更新**：2026-03-27
**状态**：draft
**来源**：抽象自当前仓库的 `ATDD-lite` 实践
**用途**：给跨项目复用的 `acceptance.md` 提供最小场景写法规则。

---

## 一、场景写法的目标

验收场景要回答的是：

**怎样才算真的通过。**

这里的“真的通过”特指 **change 正式验收通过**，不是“测试通过”或“mock 跑通”。

它不应该回答：

1. 代码内部怎样实现
2. 开发者打算怎么修

---

## 二、每个场景至少写什么

建议每个场景至少写 4 个字段：

1. 场景名称
2. 执行方式
3. 通过信号
4. 失败口径

推荐最小表头：

| ID | 场景 | 执行方式 | 通过信号 | 失败口径 |
| --- | --- | --- | --- | --- |
| A1 | 主路径成功 | 填当前项目真实入口 | 结果可观察 | 结果不满足通过信号 |

---

## 三、通过信号必须可观察

推荐通过信号来自以下几类：

1. 退出码
2. JSON 字段
3. 文件产物
4. 数据库状态
5. 日志关键字
6. 外部系统中的可观测状态变化

不推荐把测试结果当作 change 正式验收信号。`pytest`、`unittest`、`dotnet test` 适合证明 contract 或 function 被锁定，不适合单独证明“这个 change 已正式验收通过”。
同样，mock、stub、fake、monkeypatch、伪造返回值也不能作为正式验收证据。

不要写：

1. 看起来正常
2. 应该可以
3. 没报错所以算通过

---

## 四、一个场景只验证一个核心行为

推荐拆法：

1. A1 主路径成功
2. A2 次主路径成功
3. A3 关键变体成功
4. A4 关键失败路径
5. A5 另一类失败路径
6. A6 边界场景

如果一个场景同时验证太多行为，失败时通常无法快速定位根因。

默认规则：**每个 change 正式验收场景不得少于 5 个，且至少要有 1 个 failure 场景**。推荐结构仍是 `3 success + 2 failure + 1 boundary`。若少于 5 个，或完全没有 failure 场景，必须在 `acceptance.md` 中写明豁免理由、风险边界与为什么仍足以判定通过。

---

## 五、自动化是方向，不是起点

允许先手工验证，但应标清：

1. 当前是手工还是自动化
2. 证据在哪里
3. 后续是否要演进成自动化

如果依赖真实环境，也要直接写明“需真实环境”，不要伪装成已自动化覆盖。

---

## 六、正式验收与测试的边界

正式验收与测试必须拆开写，不能混用：

1. 正式验收只接受真实入口、真实环境、真实产物、真实记录与真实证据。
2. test 只用于锁定 contract 与 function，属于开发质量证据，不等于 change 验收证据。
3. mock、stub、fake、monkeypatch、假对象、伪造返回值都不能单独构成正式验收通过。
4. 如果当前只有 test 或局部预验证结果，必须在 `真实验收待办清单` 中明确还缺哪些真实执行步骤。

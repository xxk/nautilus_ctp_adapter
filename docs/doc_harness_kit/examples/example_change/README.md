# 示例变更包 / Example Change Bundle

**创建日期**：2026-03-27
**最后更新**：2026-04-02
**状态**：draft
**用途**：展示一个已经按 `templates/changes/` 填完的 child change bundle 应该长什么样，便于跨项目接入时直接对照填写。

---

## 一、这份示例怎么用

这不是当前仓库的正式 change，也不是要直接在本仓执行的任务。

它的作用是给另一个项目一个“模板填完后”的对照样板：

1. 先复制 `templates/changes/` 下的模板正文
2. 再对照本目录里的已填写样例补齐字段、场景和证据结构
3. 若你的 change 需要方案冻结，再参考本目录里的 `design.md`

---

## 二、为什么这个示例选择“统一运行入口”

因为这是大多数项目都会遇到的中风险问题：

1. 有多个历史入口
2. AI 容易改错落点
3. 验收信号相对清晰
4. 不依赖真实远端环境也能先跑本地闭环

所以它适合作为跨项目接入时的第一个试点 change。

---

## 三、这个目录展示了什么

1. `plan.md`：如何把真实交付目标拆成可执行步骤、验证动作和长期回写目标
2. `acceptance.md`：如何把“至少 5 个、且至少 1 个 failure”的正式场景、出口条件和 AI 状态板写完整
3. `ai_constraints.md`：如何把 AI 的允许范围、禁止事项和状态管理写清楚
4. `design.md`：什么情况下需要在三件套之外额外补设计文档

---

## 四、复制后必须替换的内容

1. `project-entry` 这一类示例 `topic-id`
2. 示例中的目录路径与正式入口名称
3. 示例中的验证命令
4. 示例中的长期文档路径
5. 示例中的风险与非目标

---

## 五、使用顺序

1. 先看 `plan.md`，确认任务拆分是否合理
2. 再看 `acceptance.md`，确认验收场景和出口条件是否够清楚
3. 再看 `ai_constraints.md`，确认 AI 的行为边界是否可执行
4. 若你的 change 存在方案分叉或入口容易改错，再看 `design.md`
